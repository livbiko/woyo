# Woyo Maintenance Log

## 2026-07-28 — First production deployment: live at https://225woyo.com

**Type**: HIGH risk (new production infra: OCI NLB, DNS, shared OKE cluster namespace). User confirmed domain ownership and approved deployment + DNS wiring.

**Domain**: `225woyo.com`, already registered via the same Register.com account used for tekeche.com/nouvellesdupays.com/livbiko.com/kendebabi.com (registrant confirmed by the user). `woyo.com` was checked first and found already taken by an unrelated registrant (registered since 2005).

**Architecture decision — dedicated NLB, not shared**: initially proposed reusing `nouvellesdupays-nlb` (its backend sets are pure OKE NodePorts, technically safe to share) to avoid provisioning new infra. **User explicitly rejected this** — each project gets its own dedicated NLB, matching the existing Tekeche/NouvellesDuPays pattern, regardless of technical safety. Provisioned `woyo-nlb` instead (public IP `132.145.48.100`), backend sets pointed at the same shared OKE ingress-nginx controller's NodePorts (30080/30443) — the controller itself is still shared (established, accepted pattern), only the front-door NLB is dedicated per project.

**Deploy sequence**: new `woyo` k8s namespace, dedicated Postgres StatefulSet, Docker images built via in-cluster Kaniko from `github.com/livbiko/woyo` (public repo), migrate+seed job, api/web Deployments, Ingress on the shared ingress-nginx controller, cert-manager Certificate via the existing `letsencrypt-prod` ClusterIssuer (HTTP-01, no new cert-manager install needed — reused what NouvellesDuPays's TLS automation work already put in place cluster-wide).

**Six real bugs found and fixed during the actual build/deploy, each confirmed via direct reproduction — not assumed correct from code review**:
1. `apps/web/Dockerfile`'s `COPY apps/web/...` paths assumed repo-root Kaniko context, but the build job uses `--context-sub-path=apps/web` — paths needed to be relative to that sub-path instead.
2. `apps/api/Dockerfile` copied `apps/api/node_modules` into the runtime image, but npm workspaces hoist everything to the root `node_modules` — that path is empty and the copy failed outright (`no such file or directory`).
3. `apps/web/public/` was an empty local directory, never committed to git (git doesn't track empty dirs) — the Kaniko git-context build had no `public/` at all, failing the Dockerfile's `COPY --from=build /app/public`. Fixed by adding a real `favicon.svg` and wiring it into `layout.tsx` metadata.
4. Prisma's engine binaries need `libssl`, which Alpine's `node:20-alpine` image doesn't ship — `prisma migrate deploy` crashed at runtime with "Could not parse schema engine response" (a real crash, not just the accompanying warning; `prisma generate` alone tolerated its absence during the build stage). Fixed with `apk add openssl` in both Docker stages.
5. `ts-node` failed at runtime with "Unknown file extension .ts" — Node's native loader was handling `seed.ts` instead of ts-node's register hook, most likely because `tsconfig.json` was never copied into the runtime image. Rather than patch that, switched to compiling `seed.ts` to plain JS at build time (`build:seed` npm script) and running it with `node` directly — more correct for production anyway, no dev-tooling needed at runtime.
6. `nest build`'s output landed at `dist/src/main.js` instead of the expected `dist/main.js`, crashing the api pods with `Cannot find module '/app/apps/api/dist/main.js'` — root cause: `tsconfig.json` had no `include`/`exclude`, so the underlying `tsc` swept up `prisma/seed.ts` into the same compilation, shifting TypeScript's inferred `rootDir` up one level. Fixed by scoping `tsconfig.json` to `"include": ["src/**/*.ts"]`. Verified locally (`dist/main.js` present directly) before triggering another full Kaniko cycle.

**Seventh bug — network layer, found via the exact same symptom pattern documented in NouvellesDuPays's own original NLB deployment**: after DNS and the Ingress were live, external HTTP/HTTPS traffic to `225woyo.com` timed out completely (not refused — a true TCP timeout) despite OCI reporting both backend sets healthy. Root cause: the backend-set-level `is-preserve-source` flag (a *different* setting from the NLB-level `is-preserve-source-destination`, which I had correctly set to `false` at NLB creation) defaulted to `true` on both backend sets since `oci nlb backend-set create` was never given that flag explicitly. This causes the classic asymmetric-return-routing failure — OCI's own health checks (which originate from inside the VCN) succeed regardless, only real external client traffic breaks. Fixed via `oci nlb backend-set update --is-preserve-source false` on both backend sets; HTTP started returning correct `308` redirects immediately after.

**Verification, not just "deployed and assumed"**: `openssl s_client` confirms a genuine Let's Encrypt cert (issued first attempt, no retries needed), valid 2026-07-27 to 2026-10-25. External curl checks: HTTPS root/www/api all `200`, bare HTTP cleanly redirects (`308` → `200`). Playwright screenshot of the live production homepage confirms full visual correctness (hero, 10 category cards, 6 featured businesses with real photos, stats, testimonials) with zero console/page errors. Curled all 4 hostnames sharing the ingress-nginx controller (`tekeche.com`, `api.tekeche.com`, `livbiko.com`, `nouvellesdupays.com`) after every infra change — all remained `200` throughout, zero regression on other projects.

**Outcome**: Success. `https://225woyo.com` and `https://www.225woyo.com` fully live, 23 categories / 6 cities / 25 demo businesses seeded (explicitly fictional placeholder data, not real businesses). No `ops/` change-management scripting system (Get-ChangeRisk.ps1 etc.) built for this project yet — this deployment was executed carefully by hand given the scale, but a proper recovery-point/rollback system matching NouvellesDuPays's `ops/` pattern is still a gap worth closing before further production changes.
